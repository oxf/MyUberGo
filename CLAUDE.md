# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

MyUberGo is a learning project: a distributed, event-driven clone of Uber built as independent Go microservices communicating over Kafka (async) and REST/HTTP (sync), backed by PostgreSQL (per-service schemas in one instance) and Redis. It is deliberately mid-refactor — services are in different architectural stages on purpose (see "Architectural maturity" below), so don't assume every service should look like the others.

The target system has **8 services**; **6 are implemented** (auth, ride, matching, driver, billing, location — this repo's `services/` directory). location-service is partial (Slice 1 of 4 — see "Location service status" below); Notification is planned but not scaffolded. An API Gateway (Kong) now sits in front of the 6 implemented services — see "API Gateway (Kong)" below. The full target design — per-service responsibilities, schemas, HTTP/Kafka contracts, the matching algorithm, and the phased roadmap — lives in `README.md`; don't duplicate it here. This file only calls out where the **current code** (what you'll actually be editing) diverges from that target, so you don't assume an unbuilt table/endpoint/topic already exists.

**Three docs, three jobs, don't duplicate across them.** `README.md` is the target product/architecture — what the system is meant to become. `CLAUDE.md` (this file) is current-state architectural orientation for an AI session — what's actually built, right now. **`PLAN.md`** is the open-work list only — unchecked items, nothing else; when an item is finished, it's deleted from PLAN.md, not left ticked. **`docs/CHANGELOG.md`** is the dated narrative history — bug writeups, verification notes, design rationale for passes already completed. If you're about to write more than two sentences of "here's what we found and fixed," that belongs in a new dated `docs/CHANGELOG.md` entry, not inline here.

## Glossary

Terms that collide across this codebase — each has caused a real documentation or reasoning error, so read the "not this" clause as seriously as the definition.

- **driver** — overloaded four ways, disambiguate by which store you mean: an `auth.user` row with `role = 'Driver'` (identity); a `driver.driver` Postgres row (profile: rating, vehicle, status); matching-service's `driver:{id}` Redis hash (shift status, cached owner, online rating); location-service's `loc:driver:{id}` Redis hash (last position). *Not* the same as a `driver.driver_id` — that's the role-table's surrogate id, referenced by `ride.ride.driver_id`, distinct from `auth.user.id`.
- **client** — three things: an `auth.client` Postgres row (a Client-role user's role-specific data, `ride.ride.client_id` points here); the caller of an HTTP API (any service, any role); an e2e-test `ClientActor` (a simulated user in the load generator). *Not* interchangeable with **user** — every client has a user, not every user has a client (Drivers and Admins don't).
- **status** — names six unrelated enums with no shared vocabulary: `ride.ride.status` (`Requested→Matched→InProgress→Completed`/`Cancelled`/`Failed`), `driver.driver.status` (`Offline`/`Online`/`OnRide`), a shift's status as carried on `ShiftUpdatedEvent` and cached in matching-service's Redis (`Online`/`Ended` — *not* persisted to Postgres, see "Matching algorithm status" below), `billing.invoice.status` (`open`/`paid`/`uncollectible`/`void`), `billing.payment.status` (`pending`/`processing`/`succeeded`/`failed`), `billing.psp_event`'s dedup state. Always say *whose* status.
- **failed** — four distinct terminal states, none of which imply the others: a ride matching gave up on after `MaxAttempts` (`ride.ride.status = 'Failed'`, driven by `ride.matching_failed`); a declined payment attempt (`billing.payment.status = 'failed'`, retried with backoff); an invoice the platform gave up collecting (`billing.invoice.status = 'uncollectible'`, terminal, no more retries); an outbox row that hit `defaultMaxRetries` ("parked," not literally `failed` — it's just never claimed again).
- **offer / candidate / target** — three stages of the same driver within one `BroadcastOffersHandler` round, not synonyms: a **candidate** is anyone `RankCandidates` returned from discovery; a **target** is a candidate that survived the busy/rate-limit filter and was selected by `SelectOfferTargets`; an **offer** is a target that `TryOffer` actually wrote to Redis (`driver:{id}:current_offer`) — a target can lose the `SETNX` race and never become an offer.
- **shift status vs. driver status** — two separate, non-colliding stores by design, not a data-integrity gap: matching-service's Redis `driver:{id}` hash's `"status"` field is the *shift's* status (`Online`/`Ended`, from `ShiftUpdatedEvent`), never persisted to Postgres. The *driver's* own status (`Online`/`OnRide`) lives only in `driver.driver.status` and is never written to Redis. Different keys, different stores, deliberately.
- **minor units** — every money amount repo-wide (`*_minor` columns/fields), always `int64`/`BIGINT`, always paired with a `currency`. *Not* a float, ever, in a persisted column or a wire payload — see "Money representation" below for the full invariant.
- **outbox vs. inbox** — `outbox_message` (ride/driver/billing) is the transactional-outbox pattern: domain write + event row in one transaction, published later. `billing.psp_event` is the opposite direction — an **inbox**: Stripe's async webhook callbacks land there first, deduped by Stripe's own event id, before being dispatched to the same finalize commands the synchronous path uses. The term "inbox" doesn't appear elsewhere in this codebase but is the standard name for that pattern.

## Commands

There is no root build tool or Makefile — each service is built/run independently. `.github/workflows/ci.yml` does exist (a matrix job per Go module: build/vet/test/golangci-lint, plus a `web` job) — it doesn't unify the *build*, just verifies each module independently in CI.

```bash
# Full stack (Postgres, Redis, Kafka, Kafka UI, a one-shot `migrate` service, all 6 business
# services, an API Gateway, the admin dashboard, and the observability stack: OTel Collector,
# Tempo, Loki, Prometheus, Alertmanager, Grafana)
docker-compose up --build

# API Gateway (Kong) — the only ingress for auth/ride/driver/billing/matching/location:
# http://localhost:8090/api/{auth,ride,driver,billing,matching,location}/...
# Admin dashboard: http://localhost:5173
# Kafka UI (inspect topics/consumer groups): http://localhost:8080
# Grafana (traces/metrics/logs — see "Observability (OpenTelemetry)" below): http://localhost:3000
# Prometheus: http://localhost:9090
# Postgres: localhost:5432 (postgres/postgres/postgres)
```

Per-service Go workflow (run from the service directory, e.g. `services/driver-service`):

```bash
go build ./...
go vet ./...
go run ./cmd
```

`go test ./...` from within a service directory runs real tests, not just param-parsing/DTO-mapping unit tests — every Postgres-backed service (auth, ride, driver, billing) has a testcontainers-based `persistence` suite spinning up a real ephemeral Postgres, and ride/driver/billing/matching/location all have testcontainers-based `consumers` suites against a real Kafka broker. `services/e2e-test` remains the one true end-to-end/integration check (it's the only thing that exercises the full request path through Kong across live services), but "no integration-test suite" undersells what `go test` alone already covers.

Each service is its own Go module (`auth-service`, `ride-service`, `driver-service`, `matching-service`, `billing-service`, `location-service`, `e2e-test`, plus `services/contracts`, `services/common`, and `services/observability`). They are **not** part of a single workspace — there is no root `go.work`. `services/shared` is **not** a Go module — it's SQL only (`services/shared/migrations/sql/`), mounted into the `migrate` compose service. Each service's `go.mod` pulls in `github.com/oxf/MyUber/contracts`, `github.com/oxf/MyUber/common`, and `github.com/oxf/MyUber/observability` via `replace ... => ../{contracts,common,observability}` directives, so those three modules must sit alongside each service on disk (as they do in this repo).

Dockerfiles build with the **repo root as build context** (see `docker-compose.yml`), not the service directory — e.g. `services/driver-service/Dockerfile` does `COPY services/driver-service/go.mod ...` and `COPY services/contracts /contracts` before `COPY services/driver-service .`. Keep this in mind if you touch a Dockerfile: paths are relative to repo root, not the service.

## API collection

`MyUberGo/` at the repo root is a [Bruno](https://www.usebruno.com/) collection (`.bru` files) with a folder per service — Auth, Driver, Ride, Matching, Billing, Location — plus a `Local` environment. Update it when you add/change endpoints so it stays a usable manual test client.

## Admin dashboard

`web/` at the repo root is a Vite + React + TypeScript read-only admin dashboard (Users / Drivers / Shifts / Rides / Invoices tables with server-side paging + sorting via the shared `PagedResponse[T]` envelope in `contracts/http`). It's in `docker-compose.yml` as the `web` service — a multi-stage build (`web/Dockerfile`) that runs `npm run build` and serves the static bundle from nginx on port 5173 (mapped to container port 80), matching the other services' build-a-lean-image-from-repo-context pattern rather than shipping the Vite dev server. For active frontend development (hot reload) run it manually instead, against a stack already up via `docker-compose up`:

```bash
cd web
npm install
npm run dev   # http://localhost:5173 — stop/exclude the `web` compose service first, or use a different port, to avoid a 5173 clash
```

Same-origin API proxying is implemented twice, deliberately kept in sync: the Vite dev server proxies all `/api/*` → Kong on `localhost:8090` (`web/vite.config.ts`), since `npm run dev` runs on the host; the containerized build does the same proxying in `web/nginx.conf`, pointing at the compose service name `kong:8000` instead of `localhost`, since nginx runs inside the compose network. Kong does its own path-prefix stripping and JWT verification either way, so neither proxy config needs per-service routing rules — the Go services need no CORS headers either, and that stays true regardless of Kong's route table. TypeScript DTOs in `web/src/api/types.ts` mirror `services/contracts/http` json tags — update them whenever contracts change; money fields follow the `*Minor` + `currency` convention (see "Money representation" below) and are formatted for display via `web/src/lib/money.ts`'s `formatMoney`, never divided in component state. List-endpoint paging contract (all services): 1-based `page`, `pageSize` (default 20, cap 100), `sortBy` validated against a per-endpoint whitelist, `sortDir` asc|desc. The five list endpoints (`GET /users`, `/ride`, `/driver/driver`, `/driver/driver-shift`, `/billing/invoices`) are Admin-only at the Kong gateway (see "API Gateway (Kong)" below) — the dashboard only works logged in as the seeded admin account.

## e2e-test simulator

`services/e2e-test` is a continuous client-activity simulator, not a business service: goroutine-per-actor virtual clients and drivers drive auth/driver/ride/billing/location over HTTP (reusing the `contracts/http` DTOs), deep-verify every write by reading it back, and report per-op stats. It is deliberately **not** in docker-compose — run it manually (`go run ./cmd` from `services/e2e-test`) against the running stack; see its README for config. It sits outside the 3-stage service progression (no server, no DB, no domain — just `cmd` + `internal/apiclient|actors|stats`). It also supports a one-shot **scenario mode** (`-scenario=location-radius`), separate from the continuous simulation, for assertions that need controlled positions/timing rather than endless random load — see its README's "Scenario mode" section. When you add or change a service endpoint, extend the corresponding actor/apiclient so the simulator keeps covering it.

## Architecture

### Services and ports

| Service | Port | Role |
|---|---|---|
| auth-service | 8000 | User signup/login, JWT issuance (access + refresh), refresh-token rotation, `GET /me`, `POST /logout` |
| ride-service | 8001 | Ride requests, fare/distance estimation, ride lifecycle; publishes `ride.requested`/`ride.started`/`ride.completed`/`ride.cancelled`; consumes `ride.accepted`, `payment.completed`, `ride.matching_failed` |
| matching-service | 8002 | Consumes `ride.requested`/`shift.updated`/`ride.cancelled`, matches rides to available drivers, publishes `ride.accepted` and `ride.matching_failed`; `POST /rides/{rideId}/accept` + `GET /drivers/{driverId}/offer` |
| driver-service | 8003 | Driver profiles and shifts (login/logout, rides, earnings), publishes `shift.updated` |
| billing-service | 8005 | Invoices completed/fee-bearing rides, collects via a pluggable `PaymentProvider` — `stub` or a real Stripe adapter (test-mode only), selected by the `PAYMENT_PROVIDER` env var — records a double-entry ledger; consumes `ride.completed`/`ride.cancelled`, publishes `payment.completed`/`payment.failed`; under `PAYMENT_PROVIDER=stripe` also exposes `POST /webhooks/stripe` for Stripe's async `payment_intent.*` callbacks |
| location-service | 8004 | Slice 1 of 4 (see "Location service status" below) — driver position ingest (`POST /batch`), a Redis geo index, `GET /internal/drivers/nearby` (network-isolated, no Kong route) for matching-service's geo discovery; consumes `shift.updated` to cache driver↔user identity; no Postgres yet |

`services/contracts` is a shared Go module (no `replace` of its own) holding the wire contracts every service depends on:
- `contracts/http` — REST request/response DTOs per service (`auth-service.go`, `driver-service.go`, `ride-service.go`, `matching-service.go` — `AcceptRideRequest`/`AcceptRideResponse`/`DriverOfferDto`, `billing-service.go`, `location-service.go` — `LocationPingDto`/`LocationBatchRequest`/`LocationBatchResponse`/`NearbyDriverDto`/`NearbyDriversResponse`, plus a shared `common.go`)
- `contracts/kafka` — Kafka event payloads (`ride-service.go` has `RideRequestedEvent`/`RideStartedEvent`/`RideCompletedEvent`/`RideCancelledEvent`, all carrying `ClientID` plus money fields — see "Money representation" below; `driver-service.go` has `ShiftUpdatedEvent`, now with a `Rating` field; `matching-service.go` has `RideAcceptedEvent` and `RideMatchingFailedEvent` (published when a ride exhausts its match retries, consumed by ride-service to set `status = 'Failed'` — see "Matching algorithm status" below); `billing-service.go` has `PaymentCompletedEvent`/`PaymentFailedEvent`)

Changing a field used across services means editing it once in `contracts` — both the producer and consumer(s) pick it up through the `replace` directive.

### Money representation (repo-wide invariant)

Every monetary value in every service, contract, and table follows the same shape (introduced with billing-service, 2026-07-25 — see `docs/billing/BILLING_SPEC.md` §2 for the full rationale):

- **Amount**: `BIGINT` in Postgres, `int64` in Go, always named `*_minor` (e.g. `estimated_price_minor`, `amount_minor`). **Minor units** (cents), never a float.
- **Currency**: `CHAR(3)` in Postgres, `string` in Go, ISO-4217 uppercase, always paired with its amount as a sibling field/column (never store or pass an amount without its currency). Only `EUR`/`USD` are seeded (`ride.tariff`).
- **Rounding**: do the fractional multiplication (distance/duration are genuinely fractional) in `float64`, round **once** at the very end via `math.Round`, cast to `int64`. Never persist or pass an intermediate float. See `ride-service/internal/application/command/create_ride.go`'s fare calculation for the reference implementation.
- **Splits must sum exactly**: `fee := amount * bps / 10000` (truncating integer division), `remainder := amount - fee` — never compute both sides independently, or a rounding gap can appear. See billing-service's `buildT1Legs` for the reference implementation (`PLATFORM_COMMISSION_BPS`, default 2000 = 20%).
- Contracts stay dumb structs — no shared `Money` type in `contracts` (JSON shape must stay obvious); a small `Money` value object inside one service's own `domain` package is fine.
- `web/` formats minor units to a display string **at the edge only** (`web/src/lib/money.ts`'s `formatMoney`), never divides by 100 in component state.

### API Gateway (Kong)

Kong (`gateway/kong.yml`, declarative config, `_format_version: "3.0"`) fronts all 6 implemented services (auth, ride, driver, billing, matching — as of 2026-08-08 — and, as of 2026-08-12, location) as the sole host-reachable ingress, on `:8090` (mapped from Kong's internal `:8000` in `docker-compose.yml`) — none of the 6 publish host ports at all; the only way to reach them from outside the Docker network is through Kong. matching-service's route (`/api/matching`, protected tier — `jwt` + `inject_user_headers`, same as ride/driver/billing) enforces ownership itself (`AcceptRideHandler`/`GetDriverOfferHandler` check the caller's injected `X-User-Id` against the target driverId's cached owner, threaded from driver-service via `ShiftUpdatedEvent.UserID` — see "Matching algorithm status" below), since Kong has no concept of driver ownership the way it does client/`X-Client-Id` for billing. location-service's route is anchored to exactly `POST /api/location/batch` (Slice 1's client-facing ping ingest), not a bare `/api/location` prefix — `GET /internal/drivers/nearby` has no Kong route at all and is reachable only from matching-service, over the compose network (see "Location service status" below for why the anchoring matters).

- **Public routes** (no token, IP-rate-limited): `POST /api/auth/signup`, `/login`, `/refresh` — a caller has no token yet at this point in the flow.
- **Protected routes** (`jwt` plugin + header-injecting `post-function` + per-user rate-limiting): `GET /api/auth/me`, `POST /api/auth/logout`, and everything under `/api/ride`, `/api/driver`, `/api/billing`. Kong's `jwt` plugin verifies the bearer token's signature/`exp`, matched by the token's `iss` claim against the one configured consumer (`myubergo-app`) in `gateway/kong.yml`. A shared `post-function` Lua snippet (the `&inject_user_headers` YAML anchor) then decodes the token's payload and sets `X-User-Id`/`X-User-Email`/`X-User-Role`/`X-Client-Id` on the proxied request, overwriting any of those headers the caller sent directly. `X-Client-Id` is only set for Client-role tokens (whose `client_id` claim is non-empty — see "Auth" below); ride-service's `POST /request-ride`/`DELETE /ride/{id}` and billing-service's payment-method/invoice routes read it instead of `X-User-Id`, since `ride.ride.client_id`/`billing.invoice.client_id` are `auth.client(id)`, not `auth.user(id)`.
- **Admin-only routes** (`jwt` + `inject_user_headers` + a second `&require_admin` Lua snippet + per-user rate-limiting): `GET /api/auth/users`, `GET /api/ride`, `GET /api/driver/driver`, `GET /api/driver/driver-shift`, `GET /api/billing/invoices`, `GET /api/billing/ledger/balance`. `require_admin` 403s unless the injected `X-User-Role` is `Admin`. These routes match on **path and method** (`methods: [GET]`, anchored regex paths like `~/api/ride$`), which Kong's traditional router ranks above the broader paths-only protected routes below — so e.g. `GET /api/ride` hits the admin-gated route while `POST /api/ride/request-ride` and `GET /api/ride/{id}` still hit the ordinary one.
- Longer/more-specific routes win regardless of declaration order in the file, so `/api/auth/me`/`/api/auth/logout` match ahead of the shorter public `/api/auth` route, and the admin routes above match ahead of the broader `/api/ride`/`/api/driver`/`/api/billing` routes, even though both are declared after in `kong.yml`.
- Kong has no concept of *resource ownership* (only role), so caller-scoped billing routes (`GET /invoices/{id}`, `GET /rides/{rideId}/invoice`, the payment-method routes) are authorized **in-service** against the injected `X-Client-Id`, the same pattern `ride-service`'s `cancel_ride.go` uses for ride ownership — Kong just guarantees the caller is authenticated, not that they own the thing they're asking for.
- Downstream services never validate the JWT themselves — they trust the `X-User-Id`/`X-User-Email`/`X-User-Role`/`X-Client-Id` headers Kong injects, and never check `X-User-Role` for authorization either (that's enforced entirely at the gateway via `require_admin`). This is only safe because Kong is the sole ingress: don't publish a host port for auth/ride/driver/billing-service without re-adding real auth to that service, or the trust boundary breaks.
- `JWT_SECRET` (auth-service's env var) and `gateway/kong.yml`'s `jwt_secrets.secret` are two independent config values that must be kept in sync manually (both default to `secret_change_me` locally) — and auth-service's minted `iss` claim (`"myubergo-auth"`, `auth-service/internal/infrastructure/security/jwt_issuer.go`) must keep matching the `jwt_secrets` key name in `kong.yml`, or every token fails the `jwt` plugin.

### Data model

A single Postgres instance hosts one schema per service (`auth`, `ride`, `driver`, `billing`; `matching` is referenced by matching-service SQL but not yet defined in the shared migrations — check `services/shared/migrations/sql/` before assuming a table exists). As of 2026-08-08, schema is managed via [golang-migrate](https://github.com/golang-migrate/migrate): `services/shared/migrations/sql/NNNN_<name>.{up,down}.sql`, split one file per schema (`0001_extensions`, `0002_auth`, `0003_ride`, `0004_driver`, `0005_ride_driver_fk` — the deferred `ride.ride.driver_id` FK, added once the driver schema exists — `0006_billing`, `0007_outbox_claimed_until` — cross-cutting `ALTER TABLE ... ADD COLUMN claimed_until` on all three `outbox_message` tables, the exception to "one file per schema" — `0008_ride_failed_status` — adds `'Failed'` to `ride.ride.status`'s CHECK constraint) plus seed data (admin user, tariffs) inline in the schema migration that owns it. A one-shot `migrate` compose service applies `up` before the 4 Postgres-backed app services start (`depends_on: condition: service_completed_successfully`) — `docker-compose up` alone now picks up new migration files, no `docker-compose down -v` volume wipe needed. Superseded a single hand-run `init.sql` (deleted) that predated this; testcontainers-based Go tests apply the same files via `postgres.WithOrderedInitScripts(...)` (plain `WithInitScripts` sorts by filename, which breaks past 9 migrations).

`auth.user` is the shared login identity for every role (`role CHECK IN ('Client','Driver','Admin')`) — it holds only account-level fields (email, password hash, name, phone). Each role's own data lives in a separate, surrogate-keyed table: `auth.client` and `auth.admin` (both `id UUID PK`, `user_id UUID UNIQUE FK -> auth.user`), and `driver.driver` (same shape, in the `driver` schema since driver-service owns it). `ride.ride.client_id` references `auth.client(id)`, and `ride.ride.driver_id` references `driver.driver(id)` — both are role-table ids, never `auth.user(id)`. A signup with `role: Client` creates `auth.user` + `auth.client` atomically (auth-service's `SignupHandler`, wrapped in a `TransactionManager` — see "Architectural maturity" below); a `Driver` signup only creates `auth.user`, and the `driver.driver` row comes later via `POST /api/driver/driver`, since that table lives in a schema auth-service doesn't own. There is no signup path for `Admin` — `NewUser` rejects it — the one seeded admin account (`admin@myubergo.local` / `admin123` locally) is inserted directly by `0002_auth.up.sql`.

**`billing` schema**: `customer` (one row per client per provider, `provider` is a plain string constant like `"stub"` rather than an enum, so adding a real Stripe provider later needs no migration), `payment_method` (brand/last4 display metadata only — **never** a PAN/CVC; a partial unique index `WHERE is_default AND status='active'` enforces at most one active default per client), `invoice` (`type IN ('ride_fare','cancellation_fee')`, `status IN ('open','paid','uncollectible','void')`; **`UNIQUE (ride_id, type)`** is the idempotency guard against a redelivered `ride.completed`/`ride.cancelled` Kafka event — treat a violation as a no-op success, never pre-check with a `SELECT` first, that would race a concurrent redelivery), `invoice_line`, `payment` (one row per collection attempt, never mutated except status; `UNIQUE (invoice_id, attempt_no)` and `UNIQUE (idempotency_key)`, format `invoice:{id}:attempt:{n}`), and the ledger — `ledger_account` (`type IN ('client_receivable','driver_payable','platform_revenue','psp_clearing','psp_fees','bad_debt')`, one row per `(type, owner_id, currency)`; **not** a plain `UNIQUE` constraint on that triple, since Postgres treats every `NULL owner_id` as distinct — `idx_ledger_account_unique` is a `COALESCE(owner_id, sentinel-uuid)` expression index instead), `ledger_transaction`, and `ledger_entry` (**append-only, never `UPDATE`/`DELETE`** — a correction is a new compensating transaction). Also `psp_event` — the Stripe webhook **inbox** (see "Glossary" above), deduped by Stripe's own event id, populated only under `PAYMENT_PROVIDER=stripe`. A ledger account balance is always `SUM(credits) - SUM(debits)` computed at query time (`billing-service/internal/persistence/ledger_postgres_repository.go`'s `GetBalance`), never a stored column — see `docs/billing/BILLING_SPEC.md` §4.4 for the full invariant list (every transaction's debits equal its credits; a transaction never mixes currencies; never `SUM` across currencies).

### Transactional outbox pattern

`ride-service`, `driver-service`, and `billing-service` write domain state and an outbox row in the same DB transaction, then a background worker drains `outbox_message`. That worker is **shared, not per-service**: all three use `services/common/outbox` (`worker.go`, ticker + `select` loop) — `services/{ride,driver}-service/internal/workers/` are empty directories, and only billing-service still has a service-local worker (its `ChargeWorker`).

The worker **claims and publishes in two separate steps**, deliberately: `claimBatch` opens the only transaction, selects `FOR UPDATE SKIP LOCKED` inside `TransactionManager.WithinTransaction`, stamps each row's `claimed_until` lease (2 min default) and commits; `publishOne` then publishes to Kafka via an `EventPublisher` port/adapter with **no transaction held**, and marks rows processed (or increments `retries` on failure) as standalone statements. Never move the publish back inside the claim transaction — that holds the row locks across a network call, the exact anti-pattern `charge_worker.go`'s own comment warns about. What makes publishing outside the claim safe is the lease: `GetUnprocessedBatch`'s `WHERE` clause skips rows whose `claimed_until` is still in the future. A row that fails `defaultMaxRetries` (10) times is parked — logged and skipped, never claimed again — rather than retried forever. This is how `ride.requested`, `shift.updated`, and `payment.completed`/`payment.failed` events get published reliably. `matching-service` consumes both ride/shift topics on the other end (caching driver/ride state in Redis, `internal/infrastructure/cache`) and publishes its own `ride.accepted` event, but without an outbox: it publishes directly from the `AcceptRideHandler` at the point a ride is matched, since Redis has no transaction to hide a dual write behind the way Postgres does here — see "Matching algorithm status" below for that tradeoff.

### Kafka consumer commit semantics (at-least-once, repo-wide)

All 12 Kafka consumers (`internal/consumers/*.go` across ride/driver/matching/billing/location-service) get at-least-once delivery from one shared mechanism: `services/common/kafkaconsumer`'s runner does the fetch/commit/retry loop (`kafka-go`'s `FetchMessage` + `CommitMessages`, not `ReadMessage`'s auto-commit) once, and every consumer file is a thin wrapper calling into it — none of them hand-roll fetch/commit themselves any more, which is what made this repo-wide semantic a one-file change instead of a 12-file one. On a genuine handler failure the offset is left uncommitted and the runner retries the *same* message in place (a short backoff, then re-attempt) rather than fetching and committing later messages ahead of it: Kafka's committed offset for a partition is a single cumulative cursor, not a per-message ledger, so committing a later message's offset would silently mark an earlier, still-failing one as done too. The practical consequence — a genuinely poisonous message blocks its partition rather than being silently skipped — is deliberate; there's no park/DLQ mechanism anywhere in this repo yet (same as the outbox worker's own retry-then-park behavior, see "Transactional outbox pattern" above). A deserialization failure is the one exception: it's committed immediately (a malformed payload will never parse no matter how many retries) but still gets a span and an error log with a truncated raw-payload field (`obskafka.TruncateForLog`), so a poison message is visible rather than silently dropped. This mechanism was introduced in the 2026-08 observability hardening pass — see `docs/CHANGELOG.md`'s "Observability hardening pass (2026-08-07)" entry — and later consolidated into `services/common/kafkaconsumer`.

This is what makes Kafka delivery to these 12 consumers genuinely **at-least-once**, not at-most-once — every guarded idempotent write this file documents elsewhere (`MarkRideMatched`'s `AND status = 'Requested'`, `MarkRideBilled`'s `AND bill_id IS NULL`, invoice's `UNIQUE (ride_id, type)`, the driver-status guarded transitions, matching-service's Redis upserts, location-service's owner-mapping `SET`) is what makes redelivery safe rather than a source of duplicate-processing bugs. This does **not** apply to matching-service's direct (non-outbox) `ride.accepted` publish described above — that remains a deliberate at-most-once tradeoff on the *producer* side, unrelated to this consumer-side fix.

### Architectural maturity: the 3-stage learning progression (intentional, not inconsistency)

Every service is deliberately built through 3 stages, and different services currently sit at different stages on purpose — match a service's *current* stage when extending it rather than unilaterally jumping it ahead:

- **Stage 1 — Basic/procedural**: everything in a single `cmd/main.go`. Handlers decode a request, run raw SQL directly, encode a response. No domain/application separation.
- **Stage 2 — CQRS + DDD (Clean Architecture)**: layered into `domain`/`application`(`command`+`query`)/`persistence`/`interfaces`/`infrastructure` (see "The layered pattern" below), command/query handlers wrapped with logging+metrics decorators, a `TransactionManager` for context-propagated DB transactions, graceful shutdown, and health checks.
- **Stage 3 — Production-grade advanced Go**: idiomatic concurrency has its first real instance — `matching-service`'s `BroadcastOffersHandler` fans out its offer-send loop via a plain `errgroup.Group` bounded with `SetLimit(BroadcastSize = 5)` (not `WithContext` — one target's `TryOffer` failure must not cancel the others; errors are aggregated with `errors.Join` instead, so a failed offer no longer skips arming the retry deadline) and pipelines its candidate-filtering Redis calls; `MatchRetryWorker.sweep` fans out the same way, a plain `errgroup.Group` bounded with `SetLimit(sweepConcurrency = 8)`. matching-service is still the only service with concurrent fan-out. Code generation from OpenAPI (HTTP contracts) and/or gRPC (inter-service calls) instead of hand-written structs is the remaining unstarted Stage-3 item, repo-wide. The other two original Stage-3 items are done, repo-wide, as of the 2026-08-01 observability pass (see "Observability (OpenTelemetry)" below): a real metrics/tracing/logging backend (OpenTelemetry SDK + Collector + Prometheus/Tempo/Loki/Grafana, replacing the old logging-only metrics stub) and a real liveness signal (health checkers now flip `Live: false` when a background worker goroutine exits unexpectedly, not a hardcoded `true`).

### Matching algorithm status

The README documents a full target matching algorithm (radius discovery → weighted ranking → tiered broadcast → atomic Redis accept → expanding-radius retry → per-driver rate limiting). `matching-service` now implements a simplified version of that same shape, entirely against Redis (no Postgres anywhere in this service — removed from `go.mod`, `cmd/main.go`, and `docker-compose.yml`):

- **Consumers**: `RideRequestedConsumer` (renamed from the misleading `RideAcceptedConsumer`) consumes `ride.requested`; `ShiftUpdatedConsumer` consumes `shift.updated`; `RideCancelledConsumer` consumes `ride.cancelled` (see the bullet below — this closes the gap the old draft of this section used to flag). All three honor the `topic` argument passed to `Run(ctx, topic)` (no longer hardcoded) and use a cancellable context for graceful shutdown.
- **Discovery is geo-first with a rating-only fallback (changed 2026-08-12)**: `BroadcastOffersHandler` calls location-service's `GET /internal/drivers/nearby` first, intersects the geographic candidates against `drivers:online` (via a new `DriverRepository.OnlineRatings` — location-service doesn't know shift state, that filter has always lived on the read path), and ranks with `domain.RankCandidates` (`0.5×distance + 0.5×rating`). Any failure in that path — location-service unreachable, or the availability intersect itself erroring — falls back to the original rating-only `TopOnlineDrivers` pool (`myubergo.matching.location_fallbacks` counter), never failing the ride. `ShiftUpdatedEvent` still carries the driver's `rating`; `UpsertDriver` (renamed from `CreateDriver`) still maintains `drivers:online` (driverID → rating), adding a driver on `status:"Online"` and removing them on any other status — location-service's own `loc:drivers:geo` is a separate index in a separate service, intersected at read time, never merged with this one (see "Location service status" below and `docs/location/LOCATION_SPEC.md` §5.4).
- **On `ride.requested`**: `CreateRideHandler` caches the ride into Redis (`ride:{rideId}` hash, `status:"searching"`), then `BroadcastOffersHandler` immediately runs the first offer round: discovers candidates per the bullet above, filters out already-offered/busy/rate-limited ones, offers to the top 5 (`ride:{rideId}:offered_drivers` SET, `driver:{driverId}:current_offer` STRING with a 30s TTL), and arms a retry deadline (`pending_ride:{rideId}` hash). The offer-send step is fanned out via a plain `errgroup.Group` bounded with `SetLimit(BroadcastSize)`, not sequential — see "Architectural maturity" above.
- **Broadcasting is BROADCAST-only** (top 5 at once, first accept wins) — the README's TIERED strategy (escalating tiers of drivers with per-tier timeouts) isn't implemented; see `PLAN.md`.
- **Atomic accept**: `POST /rides/{rideId}/accept` → `AcceptRideHandler` does a Redis `SET ride:{rideId}:accepted_by driverId NX` (first writer wins); 409 on a lost race, 400 on an expired/cancelled/not-offered-to-this-driver claim, 404 if the ride doesn't exist. On success it marks the ride `matched`, clears the offer/pending state, removes the driver from `drivers:online`, and publishes `ride.accepted` directly (no outbox — a deliberate at-most-once tradeoff, since Redis has no transaction to hide a dual write behind and the match itself is already durable).
- **Retry** is a background `MatchRetryWorker` (ticker+select loop, per-ride sweep fanned out via `errgroup` bounded at `sweepConcurrency`) sweeping `pending_ride:*`; a ride whose deadline lapsed without an accept gets `BroadcastOffers` re-run with `attempt+1`, capped at 5 attempts. Since 2026-08-12 this both widens the candidate pool size (`PoolWidthPerAttempt`, unchanged, also used as location-service's query `limit`) **and** expands the geo search radius (`radiusForAttempt`: 5→7→9→11→13km, cap 15) when location-service is available — on the rating-only fallback path it's pool-widening only, same as before Slice 1. On exhausting `MaxAttempts` the ride is marked `failed` in Redis **and** `ride.matching_failed` is published directly (no outbox, same at-most-once tradeoff as `ride.accepted` below) — ride-service consumes it (`FailRide`) and sets the Postgres row's `status = 'Failed'`, closing what used to be a silent dead end (added alongside migration `0008`, which added `'Failed'` to `ride.ride.status`'s CHECK constraint).
- **Rate limiting**: `driver:{driverId}:notifications:minute` INCR/EXPIRE, capped at 3/minute — implemented as a sliding window (each offer resets the 60s TTL) rather than a strict fixed window.
- **`ride:{rideId}:cancelled`**: `RideCancelledConsumer` → `CancelRideHandler` sets it on `ride.cancelled`, clears `ride:{id}:offered_drivers`/`pending_ride:{id}`, and — if the ride had already been matched — restores the accepted driver to `drivers:online`. Checked on accept (`AcceptRideHandler`) so a cancel that races an in-flight accept still loses cleanly.
- **`GET /drivers/{driverId}/offer`** lets a driver poll for their current offer (404 if none) — there's no Notification service to push offers, so polling is the only delivery mechanism for now.
- **Ownership enforcement (2026-08-08)**: both `AcceptRide` and `GetDriverOffer` now check the caller's Kong-injected `X-User-Id` against the target driverId's cached owner (`driver:{driverId}` hash's `userId` field, threaded from driver-service via `ShiftUpdatedEvent.UserID` — populated at `UpsertDriver` time) — a mismatch or missing cached `userId` is `ErrForbidden` (403). Before this, both endpoints trusted a self-asserted `driverId` with no identity check at all.
- **Shift status vs. driver status are two separate, non-colliding stores, by design** (clarified 2026-08-15, `docs/AUDIT_2026-08-15.md` #12): matching-service's `driver:{driverId}` Redis hash has a `"status"` field holding the *shift's* status (`"Online"`/`"Ended"`, from `ShiftUpdatedEvent`) — this is never persisted to Postgres (`driver.shift` genuinely has no `status` column, and nothing reads expecting one). The *driver's* own status (`Online`/`OnRide`, flipped by `ProcessRideAccepted`/`ProcessRideCompleted`/`ProcessRideCancelled` below) lives only in Postgres `driver.driver.status` and is never written to Redis at all. They don't collide because they're different keys in different stores — earlier audit language implying a shared-field collision was imprecise.
- **Now wired end-to-end on the ride side**: `ride-service` consumes `ride.accepted` (`MarkRideMatched`, flips `driver_id`/`status='Matched'`/`matched_at`, idempotent against redelivery), `payment.completed` (`MarkRideBilled`, sets `bill_id`), and `ride.matching_failed` (`FailRide`, sets `status='Failed'` — see the retry bullet above) — three consumers, three independent groups. `driver-service` also consumes `ride.accepted` (`ProcessRideAccepted`: `Online`→`OnRide`), `ride.completed` (`ProcessRideCompleted`: `OnRide`→`Online` + increments `total_rides_completed`, guarded so a redelivered event that finds the driver already `Online` skips both), and `ride.cancelled` (`ProcessRideCancelled`: `OnRide`→`Online`, no increment) — all three flip real persisted status, not placeholders. `ride.completed`/`ride.cancelled` also now drive billing-service's invoice pipeline (see "Data model" above) — the same two events, two more independent consumer groups.

Remaining work toward the README's full target: TIERED broadcast escalation (the Stage-3 concurrent fan-out for the broadcast step itself is already done, see "Architectural maturity" above) — see `PLAN.md`. Geo-based discovery is done as of 2026-08-12 (Location service Slice 1), with the caveat that it's rating+distance intersected against availability, not the README's `acceptance_rate`-inclusive formula (no data source for that third term yet).

### Location service status (added 2026-08-12, Slice 1 of 4)

`location-service` implements the design in `docs/location/LOCATION_SPEC.md` (moved from `docs/LOCATION_SPEC.md` and corrected against this codebase — its own §0.1 lists every correction with rationale; don't re-derive them). **Only Slice 1 (ingest + geo index + discovery) is built.** Slice 2 (WebSocket + live tracking), Slice 3 (Postgres `location` schema, raw history, map-matched ride summaries), and Slice 4 (Geoapify proxy) are all still open — don't assume any Postgres table, WebSocket endpoint, or Geoapify integration exists.

- **Redis-only, no Postgres, Stage 2 from day one** — same shape as matching-service (no `PG_DSN`, no `migrate` dependency), overriding this file's own "Architectural maturity" note that new services traditionally started at Stage 1 (billing-service broke that precedent first).
- **All Redis keys are prefixed `loc:`** (`loc:drivers:geo`, `loc:drivers:lastseen`, `loc:driver:{id}`, `loc:driver:{id}:owner`, `loc:user:{userId}:driver`) — deliberately, since Redis DB 0 is shared with matching-service's own unprefixed `driver:*`/`ride:*`/`drivers:online` keys and there was no existing namespace convention. Never write an unprefixed `driver:{id}` key from location-service; it would collide with matching-service's hash of the same name.
- **Ingest identity is resolved, not asserted.** A ping payload carries no `driverId` field — the handler resolves the caller's driver from Kong's injected `X-User-Id` via `loc:user:{userId}:driver`, cached from `shift.updated` (a second, independent consumer group over the same topic matching-service already consumes). An unknown caller is `ErrForbidden`/403, the same "unknown driver is a deny" rule matching-service applies, just phrased as "unknown user" since that's what Kong actually authenticates. This is a deliberate divergence from matching-service's self-assert-and-verify pattern for the analogous case (`AcceptRideHandler` checking a caller-supplied `driverId` against its cached owner) — there is no field here to assert in the first place.
- **`GET /internal/drivers/nearby` has no Kong route and never will in this design** — network-isolated, reachable only from matching-service over the compose network, same trust model as everywhere else in this repo (Kong is the sole ingress; anything without a route is unreachable from the host). **This guarantee was briefly false in practice**, not just at risk: `gateway/kong.yml`'s location route was an unanchored `/api/location` prefix with `strip_path: true`, so `GET /api/location/internal/drivers/nearby` matched it and proxied through for any valid JWT holder — the endpoint has no authorization logic of its own, since it was built assuming nothing outside the compose network could reach it. Fixed 2026-08-18 by anchoring the route to exactly `~/api/location/batch$` with `methods: [POST]`, matching the pattern the admin-only routes above already use — verify with `grep -n "location-service" gateway/kong.yml` before trusting this claim again if the route changes.
- **matching-service is the only consumer so far.** `BroadcastOffersHandler` calls it first, with a radius derived from attempt (`radiusForAttempt`: 5→7→9→11→13km, cap 15), and falls back to the pre-existing rating-only pool on any failure — see "Matching algorithm status" above for the integration details. This is the repo's first internal service-to-service HTTP call; the client lives in the new `services/common/httpclient` (timeout + otelhttp transport, no retry/circuit-breaker — the caller's fallback is the degradation path). `FindNearbyDriversHandler` also records a metric for the candidate count returned, so a thinning geo index is visible in Grafana, not just inferred from `location_fallbacks`.
- **StalenessWorker** (ticker+select, 30s default) evicts drivers who stop pinging from `loc:drivers:geo`/`loc:drivers:lastseen` — Redis GEO has no per-member TTL and no `GEODEL`, `ZREM` is the only way out. Required from Slice 1, not deferred, or a driver who force-kills the app stays in the index forever. **This is no longer the only staleness defense**: `DriverLocationRepository`'s `Nearby` also filters its own results against `loc:drivers:lastseen` at read time, dropping any member whose last-seen timestamp is already past the staleness threshold — so a driver mid-gap before the next sweep tick is excluded from discovery immediately, not just once the sweep catches up. Read the TTL-asymmetry bullet below with this in mind: it predates the read-path filter.
- **Ping validation** rejects (counted by reason, not silently dropped) out-of-range/non-finite coordinates, poor accuracy, clock skew, and implied-teleport speed; ordering is by `deviceTs` (not arrival order), last-write-wins with no Lua script. Raw `SpeedMps`/`HeadingDeg` fields are stored without any validation — no valid range for either is defined anywhere in `LOCATION_SPEC.md` §5.5; deliberately left unvalidated pending a real spec decision on bounds rather than inventing limits (`docs/AUDIT_2026-08-15.md` #10).
- **TTL asymmetry between `loc:driver:{id}` and the staleness sweep is a known, intentional tradeoff, not a bug** (`docs/AUDIT_2026-08-15.md` #9): `loc:driver:{id}`'s hash (holding `LastPosition`, used by the teleport-guard and stale-ordering-guard) expires after 5 minutes of silence, while `loc:drivers:geo`/`loc:drivers:lastseen` are only cleared by `StalenessWorker`'s sweep (~150s worst case with default settings). In practice the sweep evicts a silent driver from the geo index well before the 5-minute hash TTL fires, so the gap rarely manifests — but if a driver goes silent for 3-5 minutes and then pings again, `LastPosition` returns nil and both guards silently skip (treated as a first-ever ping) rather than blocking. Accepted as a graceful-degradation behavior; retune together if either constant changes.
- **`LocationIngestor` port is intentionally deferred** (`docs/AUDIT_2026-08-15.md` #4): the `POST /batch` handler calls the ingest command directly rather than through a port interface — functionally equivalent today since there's only one caller. Add the port when Slice 2's WebSocket adapter becomes a second caller, not before.

### The layered pattern (driver-service and billing-service; the direction matching-service is moving)

```
internal/
  domain/            entities + repository interfaces (ports), e.g. DriverRepository, ShiftRepository, OutboxRepository
  application/
    command/         one file per write use case; constructor wraps the handler with decorators
    query/            one file per read use case
    services/         cross-cutting app-layer ports, e.g. TransactionManager interface
    app.go             wires Commands/Queries structs of decorator.CommandHandler[Cmd, Result] / QueryHandler[...]
  common/
    decorator/        generic CommandHandler[C,R]/QueryHandler[Q,R] interfaces + logging, metrics & tracing decorators applied at construction time
    errors/
  persistence/        Postgres repository implementations + PostgresTransactionManager (context-based tx propagation via WithTx/context_helpers.go)
  infrastructure/      health checks, graceful shutdown, metrics client (OTel-backed)
  interfaces/http/handler/  thin HTTP handlers that decode a request, build a command/query, call application.Commands/Queries, encode the response
  workers/            service-specific background workers (ticker + `select` loop). The outbox worker no longer lives here — it's shared, in `services/common/outbox`; only billing-service's `ChargeWorker` and matching-service's `MatchRetryWorker` are still service-local
cmd/main.go           composition root: opens DB, builds repositories, wraps them into `app.Application`, registers HTTP routes, starts server + workers
```

Command/query handlers are constructed via `NewXHandler(...)` functions that build the concrete handler and immediately wrap it with `decorator.ApplyCommandDecorators`/`ApplyCommandDecoratorsNoResult` (logging + metrics) — callers only ever see the decorated `decorator.CommandHandler[C,R]` interface, never the concrete type. Follow this shape for any new command/query in driver-service or matching-service.

`services.TransactionManager.WithinTransaction(ctx, fn)` opens a Postgres tx, stashes it on the context (`persistence.WithTx`), and runs `fn`; repository methods pull the tx off the context via `context_helpers.go` so the same repository code works inside or outside a transaction.

### Observability (OpenTelemetry)

All 6 services export traces, metrics, and logs via the OpenTelemetry SDK to an OTel Collector, which fans them out to Tempo (traces), Prometheus (metrics), and Loki (logs) — Tempo, Prometheus, Loki, Alertmanager, and Grafana are all compose services (`docker-compose.yml`), config lives under `observability/` at the repo root (collector pipeline, Tempo/Loki/Prometheus config, Alertmanager routing/inhibit rules, Grafana datasource/dashboard provisioning). Grafana is at `http://localhost:3000` (anonymous Admin locally) with 4 provisioned dashboards (Platform Overview, Ride Funnel, Kafka & Outbox, Billing) under the "MyUberGo" folder. Alertmanager (`http://localhost:9093`) routes `observability/prometheus-rules.yaml`'s SLO burn-rate and operational alerts by severity.

- **Shared module**: `services/observability` (module `github.com/oxf/MyUber/observability`, wired into each service via the same `replace ... => ../observability` pattern `contracts` uses) was the first shared Go code in the repo. Packages: `otelinit` (SDK bootstrap from standard `OTEL_*` env vars, installed as the process's global providers), `obslog` (JSON logrus + OTLP log bridge + trace_id/span_id correlation), `obshttp` (otelhttp server middleware), `obsdb` (otelsql wrap for `database/sql`), `obskafka` (hand-written W3C trace-context carrier over `[]kafka.Header` — `segmentio/kafka-go` has no official OTel instrumentation), `obsdecorator` (tracing wrappers for the CQRS command/query handler decorators), `obsmetrics` (the OTel-backed `MetricsClient` implementation), `obsoutbox` (marshals/unmarshals trace context for the outbox — see below).
- **`services/common`** (module `github.com/oxf/MyUber/common`, same `replace ... => ../common` pattern) followed the same precedent for the CQRS decorator machinery itself: `commondecorator` (`CommandHandler[C,R]`/`CommandHandlerNoResult[C]`/`QueryHandler[Q,R]`, `ApplyCommandDecorators`/`ApplyCommandDecoratorsNoResult`/`ApplyQueryDecorators`, the `MetricsClient` interface, and the logging/metrics decorator structs — previously hand-copied per service) and `reqctx` (the per-request correlation-ID context helper, previously hand-copied and imported by each service's HTTP middleware). Each service's own `internal/common/decorator` package is now a thin, one-file shim (`decorator.go`) that type-aliases `commondecorator`'s generics (`type CommandHandler[C any, R any] = commondecorator.CommandHandler[C, R]`, etc. — a Go alias, not a defined type, so existing call sites keep compiling unchanged) and supplies that service's own `isExpectedError`/`isNotFound` classifier functions as parameters into `commondecorator.ApplyCommandDecorators`/etc. `internal/common/errors` stays fully per-service (deliberately out of scope — see below); `internal/common/reqctx` is deleted outright per service in favor of importing `github.com/oxf/MyUber/common/reqctx` directly.
  - **`services/common` has since grown well past those two packages — check it before writing anything that looks shared.** It now holds 16: `commondecorator` and `reqctx` (above), plus `dbconn` (Postgres bootstrap: DSN resolution, production-default guard, env-driven pool tuning — no service calls `SetMaxOpenConns` itself), `dbexec` (executor + context-carried transaction manager), `envconfig` (`String`/`Int` env helpers; note `Int` yields **0**, not the default, on an unparseable value — deliberate bug-compatibility with the helpers it replaced), `health` (the `Checker`, plus `GoSafe` — the goroutine wrapper that marks a service not-live when a worker exits unexpectedly; it is *not* a per-`cmd/main.go` helper), `httpclient`, `httpmiddleware` (`BodyLimit`/`Recover`/`RequestID`), `httpresponse`, `kafkaconsumer` (the manual fetch/commit/retry loop implementing the at-least-once semantics described above), `kafkapublisher` (one persistent `kafka.Writer` + trace-header injection), `kongheaders`, `outbox` (see "Transactional outbox pattern" above), `paging`, `pgtest` (ephemeral-Postgres bootstrap; deliberately not a `_test.go` file so it crosses module boundaries), and `shutdown`. There is no shared Redis helper yet — `redis.NewClient` is still constructed by hand in matching- and location-service, and `services/common/go.mod` has no go-redis dependency (see `PLAN.md`'s "Shared infrastructure" section).
- **The structural-typing trick**: `obsdecorator`'s `CommandHandler[C,R]`/`QueryHandler[Q,R]` interfaces are separately declared (not imported — each service is its own Go module) but method-set-identical to `commondecorator`'s own (and, via the alias, each service's local `decorator` package) types, so Go's structural interface typing makes them freely assignable both ways. Wiring tracing into `commondecorator` is a one-line addition inside `ApplyCommandDecorators`/`ApplyQueryDecorators` (`obsdecorator.TraceCommand[H, R](handler, isExpectedError)`), not a rewrite of every command/query file.
- **`decorator.MetricsClient`** (aliased to `commondecorator.MetricsClient`, no longer copy-pasted) changed shape from the old `Inc(key string, value int)` counter-only stub to `IncCounter(ctx, name string, attrs ...attribute.KeyValue)` / `RecordDuration(ctx, name string, d time.Duration, attrs ...attribute.KeyValue)` / `RecordValue(ctx, name string, value float64, attrs ...attribute.KeyValue)` — ctx enables exemplars (a latency spike in a Grafana panel links straight to a trace in Tempo), and attributes replace what used to be a cartesian product of mangled metric-name strings (`commands.createdriver.duration_ms`, `.success`, `.failure`, ...) with one histogram (`myubergo.command.duration`) sliceable by `command.name`/`outcome`. matching-service's `internal/infrastructure/metrics` still returns the concrete `*obsmetrics.Client` (not the interface) from `NewOtelMetricsClient`, unaffected by the interface's new home, so `cmd/main.go` can still reach its extra `Gauge()` method for the "drivers online" gauge.
- **Outbox trace continuity**: the transactional outbox (`ride`/`driver`/`billing`-service — see "Transactional outbox pattern" above) is the one place a live `context.Context` doesn't survive — the HTTP request that inserts an outbox row returns long before the background worker polls and publishes it. `ride.outbox_message`/`driver.outbox_message`/`billing.outbox_message` each carry a `trace_context JSONB` column (`services/shared/migrations/sql/`), populated automatically by each service's `PostgresOutboxRepository.Insert` via `obsoutbox.MarshalTraceContext(ctx)` — **must** be stored as `var traceContext any` (not `[]byte`); a nil `[]byte` boxed into a variadic `interface{}` arg is not detected as SQL NULL by `database/sql`/`lib/pq`, and silently becomes an empty (not NULL) value that fails the jsonb column's implicit text→json cast. Each outbox worker rehydrates it via `obsoutbox.UnmarshalTraceContext` before publishing, so the eventual Kafka message's `publish <topic>` producer span (and everything downstream) still joins the originating request's trace. matching-service's one direct (non-outbox) Kafka publish (`ride.accepted` in `AcceptRideHandler`) doesn't need this — its ctx is already live when it publishes.
- **Business metrics** (bounded attributes only — never an entity ID as a metric attribute, those belong on spans; this list is representative, not exhaustive — `grep -rn "myubergo\." services/*/internal` finds the current set): `myubergo.rides.{requested,completed,cancelled,failed}`, `myubergo.ride.estimated_fare_minor`, `myubergo.ride.time_to_match` (the headline product SLI, requested→matched); `myubergo.matching.{offers_broadcast,broadcast_rounds,accept_result,rides_failed,rate_limited,location_fallbacks}`, `myubergo.drivers.online` (observable gauge, `ZCARD drivers:online`); `myubergo.shifts.{started,ended}`, `myubergo.driver.status_transitions`; `myubergo.invoices.created`, `myubergo.payments.attempted`, `myubergo.payment.amount_minor`; `myubergo.signups`, `myubergo.logins`; `myubergo.outbox.{pending,parked}` (per Postgres-backed service, backed by `OutboxRepository.CountByRetries` — `parked > 0` is the signal a message hit `defaultMaxRetries`); `myubergo.location.{pings_accepted,pings_rejected,staleness_evictions,geo_index_size,ingest_lag,nearby_candidates_returned}`. Technical metrics (RED per service/operation, DB pool stats, Go runtime, Kafka consumer-group lag) are derived automatically from spans by the Collector's `spanmetrics`/`servicegraph` connectors and the `kafkametrics` receiver — no service-side code needed for those.
- **Liveness vs. readiness**: `health.Checker` — a shared `services/common/health` package, not per-service copy-paste (each service's own `internal/infrastructure/health` is a thin alias shim over it, see "Glossary"/`services/common` above) — no longer hardcodes `Live: true`. `MarkNotLive(reason)` is called by `health.GoSafe` (also shared) when a background worker (an outbox worker, a Kafka consumer, the match retry worker) returns while its context hasn't been cancelled — a genuine crash/unexpected-exit signal, idempotent (first reason wins). `MarkNotReady()` is called from `shutdownManager.OnStop` so `GET /health/ready` reflects shutdown immediately rather than waiting for the next DB/Redis-ping tick. `docker-compose.yml`'s `HEALTHCHECK` (via each service's `app healthcheck` subcommand) now probes `/health/live`, not `/health/ready` — see `docs/CHANGELOG.md`'s 2026-08-01 Tech Debt entry (Phase 1) for why it used to deliberately probe `/health/ready` instead (liveness was meaningless before this).
- **Kong**: originates the trace for every proxied request via the `opentelemetry` plugin (global, in `gateway/kong.yml`) plus `KONG_TRACING_INSTRUMENTATIONS=all`/`KONG_TRACING_SAMPLING_RATE=1.0` (`docker-compose.yml`) for Kong's own internal spans. Downstream services extract the resulting `traceparent` via `obshttp`'s otelhttp wrapper — no coordination needed beyond both ends speaking W3C Trace Context (the OTel SDK default).
- **CI/local dev**: exporter construction never fails the boot — OTLP/gRPC exporters dial lazily and retry in the background, so a down/absent Collector degrades to dropped telemetry, not a crash; this is what lets `.github/workflows/ci.yml`'s `go test` run with no Collector present and no `OTEL_SDK_DISABLED` set at all. `otelinit.Setup` does honor `OTEL_SDK_DISABLED=true` with an explicit early return (verified against the Go SDK, which does not implement this env var itself) for callers that want to skip exporter construction entirely — e.g. a test that asserts exact span/metric output would want this — but CI does not currently set it, since the lazy-dial behavior already makes it unnecessary for a plain build/vet/test/lint run.

### Auth

JWT-based (`golang-jwt/jwt/v5`), HS256, secret from `JWT_SECRET` env var (default `secret_change_me` — never rely on this outside local dev). Access + refresh tokens are both plain JWTs; refresh tokens are additionally persisted in `auth.refresh_token` so they can be revoked/validated server-side — `POST /logout` deletes one, scoped to the caller's own `X-User-Id` (never a token-body field, so a caller can only revoke their own sessions). `GET /me` returns the caller's own profile, likewise identified by `X-User-Id`, and additionally echoes `clientId` (looked up from `auth.client` by `Login`/`Refresh`/`GET /me` — never for `Driver`/`Admin` accounts, which have no client row). Every JWT's `iss` claim is `"myubergo-auth"` (`auth-service/internal/infrastructure/security/jwt_issuer.go`) and must stay in sync with the `jwt_secrets` key configured for Kong's consumer in `gateway/kong.yml`, or every token fails Kong's `jwt` plugin. A Client's access token additionally carries a `client_id` claim (empty for `Driver`/`Admin`); Kong injects it as `X-Client-Id`. Downstream services never validate the JWT themselves — Kong does that at the edge and injects `X-User-Id`/`X-User-Email`/`X-User-Role`/`X-Client-Id` from the token's own claims (see "API Gateway (Kong)" above); `ride-service`'s `POST /request-ride` reads `X-Client-Id` (not `X-User-Id`, since `ride.ride.client_id` is now `auth.client(id)`), and every other protected handler reads whichever injected header matches the id it needs.
